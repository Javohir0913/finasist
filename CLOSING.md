# Закрытие месяца

Модуль реализован: экран «Закрытие месяца» в разделе «Обзор», право
`closing:view`. Ниже — как он устроен, какие правила соблюдает и какие
грабли были убраны заранее.

## Как этим пользоваться

1. Меню → **Обзор → Закрытие месяца**.
2. Слева — все месяцы от первого месяца с данными до текущего. Очередной
   помечен «очередь», он же открывается по умолчанию.
3. Справа — проверки. Красные пункты блокируют кнопку «Закрыть месяц»,
   жёлтые предупреждают, серый — справочный.
4. «Закрыть месяц» → подтверждение → месяц закрыт. Кнопка «Открыть обратно»
   доступна только для ПОСЛЕДНЕГО закрытого месяца и только с правом
   `closing:delete`.

**Два жёстких правила:**

* закрывать только **подряд** — если данные начинаются с июня, первым
  закрывается июнь, и без него июль не закрыть;
* закрытие месяца замораживает **и все предыдущие** — иначе документ
  задним числом пересчитал бы себестоимость внутри закрытого месяца.

## 1. Как это устроено внутри

### Блокировка закрытого месяца

`app/periods.py` — единственное место, где живёт правило «закрытый месяц
не трогаем». Проверка уже подключена ко ВСЕМ эндпоинтам, которые пишут
первичку:

| Что | Где | По какой дате |
|---|---|---|
| Операции банка и кассы | `routers/transactions.py` | `doc_date` |
| Приход/расход ТМЦ, выпуск, продажа | `routers/inventory.py` | `doc_date` |
| Услуги | `routers/services.py` | `doc_date` |
| Зарплата | `routers/payroll.py` | `period` («ГГГГ-ММ») |
| Курс доллара | `routers/misc.py` | `rate_date` |
| Налоги | `routers/misc.py` | `accrued_date` |
| Займы и движения по ним | `routers/misc.py` | `opening_date` / `doc_date` |
| Входящее сальдо контрагента | `routers/organizations.py` | `opening_date` |
| Входящий остаток счёта и кассы | `routers/directories.py` | `opening_date` |
| Загрузка из Excel | `routers/imports.py` | построчно, ошибка видна в dry-run |
| Входящие остатки склада | `routers/materials.py`, `products.py`, `inventory.py` | даты нет — см. ниже |

> **Главное правило: закрыт месяц — закрыто и всё, что было раньше.**
> Не только сам закрытый месяц. Остатки и себестоимость выводятся полным
> реплеем движений с начала учёта, поэтому документ, датированный ДО закрытого
> месяца, меняет среднюю цену списаний ВНУТРИ него, а значит и его ОФР. Без
> этого правила закрытие июля обходилось бы вводом документа в июнь.

Три функции:

* `assert_open(db, *dates, what=...)` — запретить, если хоть одна дата не
  позже последнего закрытого месяца. При правке и удалении передаётся и
  СТАРАЯ дата: иначе документ можно было бы просто «вынести» из закрытого
  месяца, поменяв дату.
* `assert_period_open(db, "2026-01", what=...)` — то же, но период строкой
  (зарплата ведётся так).
* `assert_no_closed(db, what=...)` — для правок БЕЗ даты, которые задевают
  всю историю сразу (входящий остаток склада стоит в самом начале учёта).
  Запрещает, пока есть хоть один закрытый месяц.

Пока таблица `period_closes` пуста, ни одна проверка ничего не запрещает —
система ведёт себя ровно как раньше.

### Модель

```python
PeriodClose(period="2026-01", closed_at, closed_by, closed_by_name, note, snapshot)
PeriodSetting(period, key, value)   # помесячные ОС / износ / капитал
```

Таблицы создаются автоматически при старте (`Base.metadata.create_all`),
миграции руками не нужны.

### Права

`closing:view` / `closing:create` (закрыть) / `closing:delete` (открыть) —
уже в `permissions.py`, экран «Роли» подхватывает их сам.

### Эндпоинты

* `GET /api/periods` — закрытые месяцы со слепком.
* `GET /api/periods/overview` — все месяцы от первого месяца с данными до
  текущего со статусами `closed` / `next` / `waiting` (этим живёт экран).
* `GET /api/periods/checks?year=&month=` — готовность месяца: `can_close`,
  список проверок и `snapshot`.
* `POST /api/periods/{period}` — закрыть (право `closing:create`). Проверки
  выполняются заново на сервере: между открытием экрана и нажатием кнопки
  кто-то мог провести документ.
* `DELETE /api/periods/{period}` — открыть обратно (право `closing:delete`),
  только последний закрытый месяц.

Проверки (`error` — закрывать нельзя, `warn` — можно, но стоит посмотреть):

| Код | Уровень | Что означает |
|---|---|---|
| `not_closed` | error | месяц ещё не закрыт |
| `sequence` | error | это очередной месяц: закрывать можно только подряд |
| `month_ended` | error | месяц закончился (пока он идёт, документы ещё поступают) |
| `rate_month_end` | error | введён курс на последний день месяца — по нему вся переоценка |
| `no_negative_stock` | error | нет позиций в минусе (минус = себестоимость списания неверна) |
| `balance_matches` | error | актив = пассив |
| `profit_reference` | info | ОФР и прирост нераспределённой прибыли — справочно |
| `payroll_done` | warn | зарплата за месяц рассчитана |
| `cashflow_codes` | warn | у всех операций месяца есть код ДДС |

`profit_reference` намеренно НЕ равенство. Курсовая разница в ОФР считается по
методике книги (лист «Курсовая разница»): это переоценка ВСЕГО накопленного
сальдо на конец месяца, а не движение за месяц, — она не складывается по
месяцам. Баланс же ведётся в сумах и переоценки не содержит вообще. Видно на
пустом месяце: оборотов нет, прирост нераспределённой прибыли ноль, а ОФР
показывает всю накопленную переоценку (в тестовых данных за 2026-06 это
−145 534 875 сум при нулевом приросте). Поэтому строка информационная.

## 2. Очередь закрытия

`periods.period_to_close(db)` возвращает месяц, который закрывается следующим:

* закрытых месяцев ещё нет → первый месяц, в котором вообще есть данные
  (`first_data_period`: минимум по датам всех первичных документов, входящих
  сальдо и периодов зарплаты);
* иначе → месяц, следующий за последним закрытым.

Проверка `sequence` требует, чтобы закрывали именно его. Поэтому если учёт
начался в июне, июль не закроется, пока не закрыт июнь.

Открывать имеет смысл только последний закрытый месяц: блокировка идёт по
МАКСИМАЛЬНОМУ закрытому месяцу, поэтому открытие месяца из середины ничего
бы не разблокировало.

## 3. Возможное развитие

Слепок (`snapshot`) сейчас только записывается. Полезно добавить на экран
сверку слепка с текущим пересчётом: расхождение означало бы, что в закрытый
месяц всё-таки что-то просочилось — страховка на случай дыры в блокировке.

## 4. Что было починено заранее (иначе закрытие ломалось бы)

**Склад не имел истории.** `Material.stock_qty` / `avg_cost` хранят только
«сейчас», и баланс подставлял сегодняшний склад в любую дату: закрыли январь —
после февральского прихода январский баланс менялся. Теперь `app/stock.py`
делает тот же реплей движений, что и пересчёт остатков, но с отсечкой по дате;
формула средней цены общая (`apply_receipt`), поэтому оценка на сегодня
копейка в копейку совпадает с экраном «Остатки по подразделениям».

**Займы и деньги брались «как сейчас».** `ledger.cash_position(on)` и
`ledger.loan_balances_at(on)` считают остаток на дату из первички; займ,
погашенный в марте, больше не исчезает из январского баланса.

**ОС, износ и капитал — одно значение на всю историю.** Износ обновляют
каждый месяц, поэтому прошлый баланс «уезжал» после каждой правки. Теперь
значение можно задать на месяц (`PeriodSetting`, эндпоинты
`GET/PUT /api/settings/periods/...`), а `periods.setting_value(key, on)`
берёт значение месяца → ближайшее более раннее → текущее из `Setting`.

**Налоги в балансе считались за месяц, а не на дату.** Неоплаченный июньский
налог не попадал в июльский баланс, а колонка «на начало периода» брала вообще
всю историю — то есть два столбца считались по разным правилам. У
`_taxes_core` появился режим «на дату» (`on=`), баланс использует его; отчёт
«Налоги» остался периодическим, как и был. На тестовых данных это сдвинуло
прирост нераспределённой прибыли за 2026-07 с 15 498 843 на 8 465 012 сум.

**Нераспределённая прибыль — балансирующая величина.** Она сходится всегда
по построению, поэтому ошибку баланс показать не может в принципе — рассчитывать
на строку «Актив = Пассив» как на контроль полноты не стоит.

## 5. Что осознанно НЕ закрыто

**Правка карточки сотрудника** (`routers/payroll.py`, employees) не
блокируется закрытым месяцем. Сам расчёт зарплаты хранит уже посчитанные
суммы, но `division` и `expense_code` сотрудника участвуют в разнесении
затрат за прошлые месяцы. Блокировать перевод сотрудника из-за того, что
январь закрыт, — слишком грубо; если нужна строгость, добавьте
`assert_no_closed` в `update_employee` для этих двух полей.

**Переименование подразделений и кодов** (`routers/directories.py`) тоже не
блокируется: это справочники, а группировка отчётов идёт по строковому
названию. Массовое переименование задним числом изменит разрезы закрытых
месяцев.
